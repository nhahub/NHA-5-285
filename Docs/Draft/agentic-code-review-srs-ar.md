# وثيقة مواصفات متطلبات البرمجيات — المراجعة الوكيلة للشِفرة (الإصدار 1)
# Software Requirements Specification — Agentic Code Review (v1)

**الحالة:** مسودة · **النطاق:** الإصدار 1 (TypeScript/JavaScript، بصيغة GitHub Action) · **الجمهور:** المساهمون والمتبنّون في مجتمع المصادر المفتوحة

---

## 1. المقدمة

### 1.1 الغرض

تحدّد هذه الوثيقة متطلبات نظام **المراجعة الوكيلة للشِفرة (Agentic Code Review)**، وهو نظام مفتوح المصدر يُجري مراجعة أولى ذاتية التشغيل على طلبات السحب (pull requests) في GitHub. تعرّف الوثيقة دراسة الجدوى والنطاق والمتطلبات الوظيفية للإصدار الأول، وتُستخدم مرجعًا يُبنى النظام ويُختبر ويُقيَّم بالاستناد إليه. أما المتطلبات غير الوظيفية (الأداء، العزل، ميزانيات التكلفة) فتُعالَج في مرحلة منفصلة (القسم 5، مُخطَّط له).

### 1.2 الجمهور المستهدف

- **المساهمون** الذين يبنون النظام أو يوسّعونه — وهم القرّاء الأساسيون للمتطلبات الوظيفية.
- **المتبنّون** الذين يدمجون الأداة (Action) في مستودعاتهم — يخدمهم قسم النطاق والافتراضات ومتطلبات سهولة الاستخدام.
- **المراجعون/القائمون على الصيانة** الذين يقيّمون مدى مطابقة أي تغيير للمواصفات.

القرّاء الباحثون عن المبرّر التجاري يكفيهم القسمان 1 و2. أما من يتولّى التنفيذ أو الاختبار فعليه المتابعة إلى المتطلبات الوظيفية (القسم 4).

### 1.3 نطاق المنتج

يُؤتمِت نظام المراجعة الوكيلة للشِفرة مرحلةَ المراجعة الأولى على طلبات السحب، بحيث يتفرّغ المراجعون البشريون للتغييرات عالية الخطورة. يجمع النظام السياق الكامل للمستودع، ويُنفّذ الاختبارات والفحوص في بيئة معزولة (sandbox)، ويُشغّل وكيل مراجعة في سياقٍ معزول عن أي وكيل كاتب للشِفرة، ويقترح الإصلاحات على هيئة تعليقات مراجعة. يُشحَن النظام بصيغة GitHub Action باستخدام مزوّد ذكاء اصطناعي واحد مجاني/منخفض التكلفة، ويُنتج مخرجًا مقروءًا للبشر ومخرجًا منظّمًا قابلًا للقراءة آليًا. يستهدف الإصدار الأول مستودعات TypeScript/JavaScript. حدود النطاق الكاملة (داخله وخارجه) في القسم 2.3.

### 1.4 المراجع

- المراجعة الوكيلة للشِفرة — تعريف المشروع (الإصدار 1)
- المتطلبات غير الوظيفية — مرحلة مؤجَّلة (مُخطَّط لها لتصبح القسم 5)

## 2. الوصف العام

### 2.1 دراسة الجدوى (Business Case)

#### 2.1.1 تعريف المشكلة

رفع التطوير المدعوم بالذكاء الاصطناعي حجمَ طلبات السحب وعددها ارتفاعًا حادًّا، بما يتجاوز طاقة المراجعين البشريين ويُحدث اختناقًا في المراجعة. والأدوات المؤتمَتة القائمة تعالج أجزاءً من المشكلة فقط: فأدوات الفحص الساكن (linters) تلتقط أخطاء الصياغة لكنها تُغفل الدلالة والاعتماديات العابرة للملفات؛ ومراجِعو النماذج اللغوية أحاديو اللقطة يقدّمون تعليقات سطحية على السطور دون تنفيذ الشِفرة أو فهم المستودع الأوسع، بل ويقعون — حين يكتب النموذجُ نفسه الشِفرةَ ويراجعها — في انحياز التأكيد الذاتي. لا توجد أداة متاحة ومراعية للميزانية تُجري مراجعة أولى ذاتية التشغيل حقًّا، واعية بالسياق، ومسنودة بالتنفيذ، مع إبقاء تركيز البشر على التغييرات التي تحمل الخطر فعلًا.

#### 2.1.2 الأهداف

1. **أتمتة المراجعة الأولى** كي يُحفَظ انتباه البشر للتغييرات عالية الخطورة.
2. **إسناد المراجعات إلى سياقٍ وتنفيذٍ حقيقيين** — سياق كامل للمستودع، وتحليل واعٍ بالاعتماديات، وتشغيل الاختبارات/البناء/الفحص في بيئة معزولة، بدلًا من الاستدلال النصّي وحده.
3. **إزالة انحياز التأكيد الذاتي** بتشغيل وكيل المراجعة في سياق جديد معزول عن أي وكيل كاتب للشِفرة.
4. **الفرز حسب نطاق الأثر (blast radius)** — توجيه طلبات السحب حتميًّا بحيث تنال التغييرات الحرجة (الأمان، المنطق الجوهري) مراجعةً أعمق، وتُمرَّر التافهة (التوثيق، ترقيات الاعتماديات) على مسار سريع.
5. **اقتراح إصلاحات قابلة للتنفيذ** على هيئة تعليقات مراجعة، مسنودة بأدلة التنفيذ (المعالجة ذاتية التطبيق مؤجَّلة للإصدار 2).
6. **العمل ضمن ميزانية مجانية/بحدود 20 دولارًا** باستخدام مزوّد واحد مجاني/منخفض التكلفة (مثل الطبقة المجانية من NVIDIA NIM)، مع تغليف نداءات النموذج خلف واجهة رفيعة تتيح تبديل المزوّد لاحقًا دون إعادة هيكلة.
7. **إنتاج مخرَج مزدوج** — ملخّصات للبشر وبيانات منظّمة للأتمتة اللاحقة.
8. **الإطلاق كمشروع مفتوح المصدر قابل للاستخدام** — توثيق واضح، وتبنٍّ سهل، وأساس قابل للتوسعة يبني عليه الآخرون.

#### 2.1.3 معايير النجاح

- تشغيل الأداة من طرفٍ إلى طرف على مستودع عام باستخدام الطبقات المجانية فقط.
- استناد المراجعات إلى نتائج اختبار/بناء مُنفَّذة فعليًّا، لا إلى الاستدلال النصّي وحده.
- إصدار النتائج وفق نموذج النتائج المعياري (القسم 4، FR-0) وتسلسلها إلى JSON مطابق للمخطَّط.
- تمكُّن مساهم جديد من تبنّي الأداة باستخدام ملف README والمخطَّط النموذجي لسير العمل والتوثيق المشحون معها.

*(الأهداف الكمّية لهذه المعايير مؤجَّلة إلى مرحلة المتطلبات غير الوظيفية.)*

### 2.2 منظور المنتج

النظام عبارة عن GitHub Action قائم بذاته، لا خدمة مُستضافة. يعمل داخل خط التكامل المستمر (CI) لدى المتبنّي على منصّات تشغيل GitHub، ويستدعي مزوّد ذكاء اصطناعي خارجيًّا عبر الشبكة. لا يحتفظ بأي حالة دائمة على جانب الخادم؛ إذ يعيش سجلّ المراجعة في تعليقات طلب السحب ومخرجات كل تشغيلة. يضع هذا الإصدارَ الأول عمدًا دون تعقيد تطبيق GitHub App المُستضاف (خطّافات الويب، خلفية، قاعدة بيانات)، وهو خارج النطاق.

### 2.3 حدود النطاق

#### 2.3.1 داخل النطاق (الإصدار 1)

- أداة GitHub Action تُشغَّل عند فتح/تحديث طلب السحب
- جمع السياق: سحب المستودع، وتحليل الشجرة النحوية المجرَّدة/الاعتماديات عبر `tree-sitter` (لِـ TS/JS)
- تنفيذ معزول للاختبارات وفحوص البناء والفحوص الأمنية الأساسية على منصّات تشغيل GitHub
- وكيل مراجعة بسياق جديد، منفصل عن تأليف الشِفرة
- فرز خطورة حتمي حسب نطاق الأثر يقود عمق المراجعة (واختياريًّا اختيار نموذج أخفّ مقابل أقوى)
- تكامل مع مزوّد نموذج واحد (مثل الطبقة المجانية من NVIDIA NIM)، مُغلَّف خلف واجهة رفيعة سهلة التبديل
- تقديم اقتراحات الإصلاح على هيئة تعليقات مراجعة (بما فيها كتل التغيير المقترَح حيثما أمكن)
- مخرَج مزدوج: تعليق ملخّص على طلب السحب + مخرَج JSON منظّم
- مكتبة أنماط قابلة للضبط تحوي أمثلة «خطأ مقابل صواب»
- دعم TypeScript/JavaScript حصريًّا
- أساسيات المشروع مفتوح المصدر: README، وLICENSE، وتوثيق استخدام، وملف سير عمل نموذجي

#### 2.3.2 خارج النطاق (الإصدار 1)

- المعالجة المؤتمَتة/ذاتية التطبيق وحلقات الإصلاح-والتحقّق (مؤجَّلة للإصدار 2)
- اللغات غير TS/JS
- تطبيق GitHub App مُستضاف بخطّافات ويب وخلفية دائمة
- لوحة تحكم ويب / واجهة تحليلات
- المنصّات غير GitHub (GitLab، Bitbucket)
- التحليل متعدّد الوسائط / تحليل المخطّطات المعمارية — مؤجَّل
- حوكمة الفِرَق، والتحكّم بالوصول حسب الأدوار (RBAC)، وميزات الامتثال والتدقيق
- بنية تحتية معزولة ذاتية الاستضافة (gVisor / Firecracker)
- توجيه متعدّد المزوّدين، وسلاسل التحويل الاحتياطي، وتجريد المزوّد المُدار بالإعدادات

### 2.4 أصحاب المصلحة

| صاحب المصلحة | المصلحة |
|---|---|
| القائمون على صيانة المستودعات | تقليل عبء المراجعة؛ فرز أولي جدير بالثقة |
| مؤلّفو طلبات السحب (بشرًا ومدعومين بالذكاء الاصطناعي) | تغذية راجعة سريعة وقابلة للتنفيذ ومسنودة بالتنفيذ |
| مساهمو المصادر المفتوحة | شِفرة ومتطلبات واضحة وقابلة للتوسعة |
| القائم على صيانة المشروع | إصدار أول قابل للشحن ومقيَّد بالميزانية وقابل للصيانة |

### 2.5 الافتراضات والقيود

- الميزانية محدودة بالطبقات المجانية / خطة واحدة بنحو 20 دولارًا؛ دون وحدات معالجة رسومية مخصّصة أو بنية استدلال مدفوعة.
- يعمل على حوسبة GitHub Actions المجانية؛ ووقت التنفيذ وموارده مقيَّدة بحدود منصّة التشغيل.
- يتطلّب مستودعات ذات مجموعة اختبارات قابلة للتشغيل كي يضيف التحقّق المسنود بالتنفيذ قيمةً.
- بوصفه أداة مفتوحة المصدر، يجب التعامل مع مفاتيح واجهة النموذج عبر أسرار المستودع/المؤسسة (secrets)، لا تضمينها في الشِفرة إطلاقًا.
- الإصدار الأول أحادي المزوّد وأحادي اللغة بقرار نطاقٍ مقصود، لا لقيدٍ تقني.

### 2.6 بيئة التشغيل

- **المنصّة:** GitHub (منصّات التشغيل المُستضافة، وActions، وواجهة برمجة طلبات السحب).
- **أحداث التشغيل:** طلب السحب `opened` و`synchronize`.
- **الاعتمادية الخارجية:** مزوّد نموذج ذكاء اصطناعي واحد يمكن الوصول إليه عبر HTTPS (الطبقة المجانية من NVIDIA NIM افتراضيًّا).
- **المستودعات المستهدَفة:** مشاريع TypeScript/JavaScript ذات سكربت اختبار قابل للتشغيل.

## 3. المسرد (Glossary)

| المصطلح | التعريف |
|---|---|
| **المراجعة الوكيلة للشِفرة (Agentic code review)** | مراجعة مؤتمَتة تجمع سياق المستودع، وتنفّذ الأدوات (اختبارات/بناء/فحوص)، وتستدلّ من النتائج — بخلاف الفحص الساكن أو تعليق النموذج اللغوي أحادي اللقطة. |
| **الشجرة النحوية المجرَّدة (AST)** | تمثيل شجري مُبنيَن للشِفرة المصدرية يُستخدم لتحليل الرموز والاعتماديات والبنية. يُنتَج هنا عبر `tree-sitter`. |
| **نطاق الأثر (Blast radius)** | مدى تأثير التغيير المحتمَل، يُستخدَم لإسناد درجة خطورة وتوجيه عمق المراجعة. |
| **جامع السياق (Context Gatherer)** | المكوّن الذي يسحب طلب السحب، ويحلّل الملفات المتغيّرة، ويجمّع السياق العابر للملفات. |
| **نموذج النتائج (Finding model — FR-0)** | التمثيل الداخلي المستقلّ عن المزوّد لكل نتائج المراجعة؛ البنية المعياريّة الوحيدة التي تُشتقّ منها المخرجات اللاحقة. |
| **المراجعة بسياق جديد (Fresh-context review)** | تشغيل وكيل المراجعة في سياق معزول عن أي وكيل كاتب للشِفرة، تفاديًا لانحياز التأكيد الذاتي. |
| **وكيل المراجعة بسياق جديد (Fresh-Context Review Agent)** | المكوّن الذي يُنتج النتائج من السياق المجموع وأدلة التنفيذ ومكتبة الأنماط. |
| **أداة GitHub (GitHub Action)** | وحدة سير عمل ضمن خط تكامل المستودع؛ وهي شكل النشر في الإصدار الأول (بخلاف تطبيق GitHub App المُستضاف). |
| **مكتبة الأنماط (Pattern library)** | مجموعة قابلة للضبط من أمثلة «خطأ مقابل صواب» ومعايير المشروع يطبّقها الوكيل عند توليد النتائج. |
| **طلب السحب (PR)** | مجموعة تغييرات مقترَحة على المستودع، وهي وحدة المراجعة في النظام. |
| **درجة الخطورة (Risk tier)** | تصنيف حتمي (مثل تافه/عادي/حرج) يقود عمق المراجعة واختيار النموذج اختياريًّا. |
| **محرّك المعالجة (Remediation Engine)** | المكوّن المسؤول عن اقتراحات الإصلاح؛ ويقتصر في الإصدار الأول على اقتراحات تعليقات استشارية (التطبيق الذاتي مؤجَّل للإصدار 2). |
| **كتلة التغيير المقترَح (Suggested-change block)** | ميزة في تعليقات مراجعة GitHub تقترح تعديلًا محدَّدًا موضعيًّا يمكن للمؤلّف قبوله مباشرةً. |
| **بيئة الأدوات المعزولة (Tool Sandbox)** | بيئة التنفيذ المعزولة (منصّة تشغيل GitHub في الإصدار الأول) التي تُجرى فيها الاختبارات والبناء والفحوص. |
| **`tree-sitter`** | مكتبة تحليل نحوي تزايُدي تُستخدَم لبناء الأشجار النحوية لتحليل الاعتماديات والبنية. |
| **يجب/ينبغي (Must/Should)** | وسمَا أولوية المتطلَّب: **يجب** = جوهري للإصدار الأول؛ **ينبغي** = ضمن الإصدار الأول إن سمح الوقت. |
| **متطلَّب غير وظيفي (NFR)** | متطلَّب غير وظيفي (الأداء، العزل، التكلفة، زمن الاستجابة) — يُعالَج في مرحلة منفصلة. |

## 4. المتطلبات المحدَّدة (الوظيفية)

تُكتَب المتطلبات على هيئة عبارات «يجب على النظام أن…» قابلة للاختبار، مجمَّعة حسب المكوّن ومربوطة بمعمارية الوحدة 2. ويُوسَم كلٌّ منها بـ**يجب** (جوهري للإصدار 1) أو **ينبغي** (ضمن الإصدار 1 إن سمح الوقت). أما العتبات المحدَّدة (ميزانيات الوقت/الذاكرة، ضمانات العزل) فمؤجَّلة إلى القسم 5 (مرحلة المتطلبات غير الوظيفية).

### 4.0 FR-0 — نموذج البيانات المعياري (نموذج النتائج)

البنية المعياريّة الوحيدة لكل نتائج المراجعة. تُعرَّف هنا مرّةً واحدة؛ ويشير إليها كل متطلَّب آخر بدلًا من إعادة تعريفها.

- **FR-0.1 (يجب)** يجب على النظام تعريف تمثيل داخلي للنتائج مستقلّ عن المزوّد («نموذج النتائج») بوصفه البنية المعياريّة الوحيدة لكل نتائج المراجعة.
- **FR-0.2 (يجب)** يجب تحويل كل مخرجات النموذج إلى نموذج النتائج قبل أي استخدام لاحق؛ ولا يجوز لأي مكوّن أن يستهلك استجابات المزوّد الخام مباشرةً.
- **FR-0.3 (يجب)** يجب أن يكون دمج مزوّد جديد ممكنًا عبر ربط مخرجاته بنموذج النتائج دون تغييرات في المكوّنات اللاحقة.
- **FR-0.4 (يجب)** يجب أن يمتلك نموذج النتائج مخطَّطًا موثَّقًا ومُصدَّرًا (versioned) يحمل حقل إصدار المخطَّط.

### 4.1 FR-1 — التشغيل والتكامل

- **FR-1.1 (يجب)** يجب على النظام أن يعمل بصيغة GitHub Action يُشغَّل عند حدثَي طلب السحب `opened` و`synchronize` (إيداعات جديدة).
- **FR-1.2أ (يجب)** يجب على النظام قراءة الإعدادات من `.agentic-review.yml` في جذر المستودع عند وجوده.
- **FR-1.2ب (يجب)** عند غياب الملف، يجب على النظام تطبيق إعدادات افتراضية مدمجة وموثَّقة.
- **FR-1.2ج (يجب)** عند وجود الملف مع غياب حقلٍ ما، يجب على النظام تطبيق القيمة الافتراضية الموثَّقة لذلك الحقل.
- **FR-1.2د (يجب)** عند وجود الملف مُعطوبًا (YAML أو مخطَّط غير صالح)، يجب على النظام الإخفاق برسالة خطأ تحدّد الحقل المخالف، وألّا يلجأ إلى بديل بصمتٍ.
- **FR-1.3 (يجب)** يجب على النظام المصادقة لدى مزوّد النموذج باستخدام سرّ مستودع/مؤسسة، لا مفتاح مضمَّن في الشِفرة إطلاقًا.
- **FR-1.4 (ينبغي)** ينبغي أن يتيح النظام تخطّي الأداة عبر وسم أو راية إعداد (مثل `skip-agentic-review`).

*(قيم الإعدادات الافتراضية الموثَّقة تعيش في ملحق مخطَّط الإعدادات، لا في نصّ المتطلَّب.)*

### 4.2 FR-2 — جمع السياق

- **FR-2.1 (يجب)** يجب على النظام سحب فرع طلب السحب وتحديد الملفات المتغيّرة وكتل الفروق (diff hunks).
- **FR-2.2 (يجب)** يجب على النظام بناء شجرة نحوية عبر `tree-sitter` للملفات المتغيّرة من TS/JS.
- **FR-2.3أ (يجب)** لكل رمز مُعدَّل في الفروق، يجب على النظام تحديد الملفات التي تستورد ذلك الرمز أو تصدّره.
- **FR-2.3ب (يجب)** لكل دالّة أو توصيف (method) مُعدَّل، يجب على النظام تحديد مواضع استدعائه المباشرة داخل المستودع.
- **FR-2.3ج (يجب)** يجب على النظام تضمين مصدر هذه التعريفات ومواضع الاستدعاء ذات الصلة في سياق المراجعة المُمرَّر إلى الوكيل، حتى سقف السياق (FR-2.5).
- **FR-2.3د (ينبغي)** ينبغي أن يسجّل النظام أيّ الملفات ذات الصلة أُدرجت ولماذا (مستورَد-بواسطة / يستدعي / مُستدعىً-بواسطة)، لأغراض التتبّع.
- **FR-2.4 (ينبغي)** ينبغي أن يُضمّن النظام السياق المحيط ذا الصلة (حدود الدوال/الأصناف، تعريفات الأنواع) بدلًا من نوافذ سطور خام.
- **FR-2.5 (ينبغي)** ينبغي أن يحدّ النظام من حجم السياق ليبقى ضمن حدود الرموز (tokens) لدى النموذج وحدود منصّة التشغيل، مع تدهور رشيق عند التجاوز.

### 4.3 FR-3 — فرز الخطورة (نطاق الأثر)

- **FR-3.1 (يجب)** يجب على النظام تصنيف كل طلب سحب حتميًّا إلى درجة خطورة (مثل تافه/عادي/حرج) باستخدام قواعد مسار الملف ونوع التغيير.
- **FR-3.2 (يجب)** يجب أن تكون قواعد الفرز قابلة للضبط (أنماط المسارات ← درجة الخطورة) كي تتمكّن المشاريع من وسم مسارات الأمان/الجوهر بأنها حرجة.
- **FR-3.3 (يجب)** يجب على النظام توجيه عمق المراجعة حسب الدرجة (تمرير سريع للتغييرات التافهة، ومراجعة أعمق للحرجة).
- **FR-3.4 (ينبغي)** ينبغي أن يختار النظام اختياريًّا نموذجًا أخفّ مقابل أقوى حسب الدرجة.

### 4.4 FR-4 — التنفيذ المعزول

- **FR-4.1 (يجب)** يجب على النظام تشغيل مجموعة اختبارات المشروع في منصّة التشغيل المعزولة والتقاط نتائج النجاح/الإخفاق ومخرجاتها.
- **FR-4.2 (يجب)** يجب على النظام تشغيل فحوص البناء/الأنواع (مثل `tsc`) والتقاط نتائجها.
- **FR-4.3 (ينبغي)** ينبغي أن يشغّل النظام `npm audit` ويلتقط نتائجه.
- **FR-4.4أ (يجب)** يجب على النظام فرض ميزانية وقت قابلة للضبط على مرحلة التنفيذ وإنهاء التنفيذ عند تجاوزها.
- **FR-4.4ب (يجب)** عند الإنهاء بسبب انتهاء المهلة، يجب على النظام وسم التنفيذ بأنه `timed-out`، وتخطّي الفحوص المتبقّية، والاستمرار في إنتاج مراجعة تُبلِغ عن انتهاء المهلة.
- **FR-4.5أ (يجب)** يجب على النظام أن يسجّل، لكل فحص، ما إذا كان قد شُغِّل أو تُخطّي أو أخفق.
- **FR-4.5ب (يجب)** يجب على النظام تسجيل نتيجة النجاح/الإخفاق لكل فحص مُنفَّذ ومخرجاته الملتقَطة.
- **FR-4.5ج (يجب)** يجب على النظام إتاحة سجلّ التنفيذ هذا لوكيل المراجعة (FR-5) وتضمينه في المخرَج المنظّم (FR-8.2).

*(ضمانات العزل وقيم ميزانية الوقت/الموارد المحدَّدة مؤجَّلة إلى القسم 5، مرحلة المتطلبات غير الوظيفية.)*

### 4.5 FR-5 — وكيل المراجعة بسياق جديد

- **FR-5.1 (يجب)** يجب أن يعمل وكيل المراجعة في سياق معزول عن أي وكيل كاتب للشِفرة (دون تاريخ/حالة مشتركة).
- **FR-5.2 (يجب)** يجب أن تحتوي كل نتيجة على: مسار الملف، والسطر أو نطاق السطور، ودرجة الخطورة، والفئة، والمسوّغ، و(اختياريًّا) مرجع إصلاح مقترَح — مطابِقةً لنموذج النتائج (FR-0).
- **FR-5.3 (يجب)** يجب أن يُدمِج الوكيل نتائج التنفيذ (FR-4) وقواعد مكتبة الأنماط (FR-6) في نتائجه.
- **FR-5.4 (ينبغي)** ينبغي أن يميّز الوكيل بين المشكلات الحاجبة والاقتراحات غير الحاجبة.
- **FR-5.5 (ينبغي)** ينبغي أن يتجنّب الوكيل التعليقات المكرَّرة/شبه المكرَّرة على النتائج غير المتغيّرة عبر عمليات إعادة التشغيل.
- **FR-5.6 (يجب)** يجب أن يطابق مخرَج الوكيل نموذجَ النتائج (FR-0)؛ وتُشتقّ مخرجات القسم 4.8 منه، لا أن يُنتجها النموذج استقلالًا.

### 4.6 FR-6 — مكتبة الأنماط

- **FR-6.1 (يجب)** يجب على النظام تحميل مكتبة أنماط قابلة للضبط من أمثلة «خطأ مقابل صواب» ومعايير المشروع.
- **FR-6.2أ (يجب)** عند توليد نتيجة من قاعدة في مكتبة الأنماط، يجب أن تشير النتيجة إلى مُعرِّف القاعدة المطابِقة.
- **FR-6.2ب (يجب)** يجب أن يدعم النظام مجموعة انحدار (regression set) من أمثلة الأنماط ذات النتائج المتوقَّعة، قابلة للتشغيل كاختبار، كي يمكن التحقّق من سلوك مطابقة الأنماط ومراقبته عبر التغييرات.
- **FR-6.2ج (ينبغي)** ينبغي أن يُبلِغ النظام عن تغطية مكتبة الأنماط (أيّ القواعد أُطلِقت) في المخرَج المنظّم.
- **FR-6.3 (ينبغي)** ينبغي أن يشحن النظام مجموعة أنماط افتراضية لـ TS/JS يمكن للمشاريع توسيعها أو تجاوزها.

### 4.7 FR-7 — اقتراحات الإصلاح (تعليقات فقط في الإصدار 1)

- **FR-7.1 (يجب)** يجب على النظام اقتراح الإصلاحات على هيئة تعليقات مراجعة، مستخدمًا كتل التغيير المقترَح في GitHub حين يكون الإصلاح تعديلًا موضعيًّا.
- **FR-7.2 (يجب)** يجب أن تكون الاقتراحات استشارية فقط — فلا يودِع النظام أو يدفع أو يطبّق تغييرات تلقائيًّا في الإصدار الأول.
- **FR-7.3 (ينبغي)** ينبغي أن يربط كل اقتراح بالنتيجة والدليل الذي حفّزه.

### 4.8 FR-8 — المخرَجات

- **FR-8.1أ (يجب)** يجب على النظام نشر تعليق ملخّص واحد بالضبط لكل تشغيلة مراجعة على طلب السحب.
- **FR-8.1ب (يجب)** يجب أن يذكر التعليق الملخّص درجةَ الخطورة، والفحوصَ المُشغَّلة ونتائجها، وعددَ النتائج حسب الخطورة، وحُكمًا إجماليًّا.
- **FR-8.1ج (ينبغي)** عند إعادة التشغيل، ينبغي أن يُحدِّث النظام تعليقه الملخّص القائم بدلًا من نشر تعليق جديد.
- **FR-8.2أ (يجب)** يجب على النظام تسلسل نموذج النتائج (FR-0) إلى JSON بوصفه مخرَجًا قابلًا للقراءة آليًّا.
- **FR-8.2ب (يجب)** يجب أن يطابق JSON مخطَّطَ نموذج النتائج المُصدَّر (FR-0.4)، شاملًا النتائج ودرجات الخطورة وسجلّ الدليل/التنفيذ ونتيجة الفرز.
- **FR-8.3 (ينبغي)** ينبغي أن يضبط النظام حالة/فحصًا غير حاجب يلخّص حصيلة المراجعة.
- **FR-8.4 (ينبغي)** ينبغي أن يكون مخطَّط المخرَج المنظّم موثَّقًا ومُصدَّرًا (انظر FR-0.4).

### 4.9 FR-9 — قابلية الاستخدام مفتوح المصدر

- **FR-9.1 (يجب)** يجب أن يُشحَن النظام مع README، وLICENSE، وتوثيق استخدام، وملف سير عمل نموذجي.
- **FR-9.2 (يجب)** يجب أن يعمل النظام على مستودع عام باستخدام الطبقات المجانية فقط (منصّة تشغيل GitHub + مزوّد نموذج مجاني).
- **FR-9.3 (ينبغي)** ينبغي أن يوفّر النظام رسائل إخفاق واضحة عند غياب المتطلَّبات المسبقة (مثل سكربت الاختبار أو مفتاح الواجهة).
